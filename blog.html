Riding Two Mac minis:
A Distributed Qwen3 Agent Server for opencode

We turned two Mac minis connected by a single Ethernet cable into one sharded, tool-calling LLM inference server — and pointed opencode at it so an AI agent can drive it end to end.

Nodes 2 × Mac mini (M2 Pro 8GB + M4 16GB) Model Qwen3-1.7B-4bit (MLX) Interconnect 1000baseT ring Turn time 3.5s wired / 34s WiFi / 1.4s single

1 The Mission

We had two Mac minis sitting in the same room and a hunch: a direct Gigabit Ethernet cable between them could fuse their Apple Silicon into a single distributed MLX compute pool. The goal was not just to shard a model and generate text — it was to build something usable as an agent:

  • Tensor-parallel inference across both machines (each holds a slice of the weights).
  • A real tool-calling loop (the model issues tool_calls, executes them, and answers).
  • Exposed as an OpenAI-compatible HTTP API so opencode — an agentic coding CLI — can treat it as its own model provider.
  • Reachable from any laptop on WiFi, while the two Macs keep talking to each other over Ethernet.

The result: a private, on-prem "model server" that opencode uses for real agentic work, with dashboards a keystroke away.

2 The Hardware

Two distinct networks carry different traffic. The control/API plane lives on WiFi (192.168.1.x); the data plane — the sharded-compute chatter between the two Macs — lives on a direct Ethernet cable (10.0.0.x).

Fig 1. Three planes: SSH control & the HTTP API over WiFi (192.168.1.x), sharded compute over the Ethernet ring (10.0.0.x).

4 Distributed Architecture

mlx.launch reads hosts.json, opens an SSH session per rank, and runs the same command on every host. Each rank initializes the distributed group (mx.distributed.init()) and cooperates through all_sum-style collectives over the ring — that's how tensor parallelism stays in sync without a central aggregator.

Fig 2. One model, two machines. Every token is computed cooperatively; only rank 0 exposes the API.

A surprising and important detail lives at mlx_lm/server.py:1745:

if group.rank() == 0:
    _run_http_server(host, port, response_generator)   # rank 0 serves the API
else:
    response_generator.join()                           # everyone else just computes

So even though both ranks load the sharded model and co-compute every forward pass, only rank 0 listens on the network. External clients always talk to rank 0; rank 1 is a silent worker. This becomes the single most confusing fact when you try to reach the "other" Mac's IP (more in section 9).

5 The Journey

Step 1 · Recon
Both Macs mapped

Verified: both arm64 on macOS 26.5.1; passwordless SSH in both directions; bidirectional TCP over the cable confirmed. Note the dead end we dodged: no Thunderbolt cable was available (only USB-A → USB-C), so IP-over-Thunderbolt was off the table — a plain Gigabit Ethernet cable became the ring.

Step 2 · Provision
Identical venvs on both nodes

Installed MLX 0.32.0 + mlx_lm 0.31.3 into .venv/ (now at the repo root) on both Macs and cached Qwen3-1.7B-4bit on both. Same path, same bits — sharded loading assumes it.

Step 3 · Smoke test
Prove the ring actually works

smoke.py ran an all_sum across ranks. Rank 0 got the summed value — proof the two machines were one collective. --python flag ignored by mlx.launch in 0.32.0 cost us a code-127 detour first.

Step 4 · Agent demo
Tool calling, distributed

agent.py ran the Qwen3 tool-loop (get_weather + calculate) sharded over both machines: parse <tool_call> JSON, execute, feed results back. Output was identical to single-node — but the ring was still on WiFi.

Step 5 · WiFi → Ethernet
The 10× speedup

Re-pointed the ring from WiFi to the direct cable (10.0.0.1 ↔ 10.0.0.2). Turn time collapsed from 34s to 3.5s with byte-identical output.

Step 6 · Serve it
Distributed OpenAI-compatible API

Launched mlx_lm.server through mlx.launch. It self-detects distribution via mx.distributed.init().size() > 1. Verified /v1/models, tool calls, and SSE streaming.

Step 7 · Agent-ify opencode
Custom provider config

Registered mlx-dist (an @ai-sdk/openai-compatible provider) pointing at rank 0, model with tool_call: true. Restarted opencode — and agentic work now runs on the cluster.

Step 8 · Go wireless
Any laptop on the LAN

Rebound the server to 0.0.0.0, verified inference over the WiFi IP, and shipped a remote config that points at http://192.168.1.64:8080/v1.

Step 9 · Observability
Metrics into Grafana — locally

Explored the k0s cluster's Prometheus + Grafana, then stood up a self-contained VictoriaMetrics + otel-collector + Grafana stack on podman (see section 11) so the Macs don't depend on the cluster at all.

6 Performance

The headline number: on a direct Gigabit link, the two-machine cluster runs ≈2.4× slower than a single node but ≈10× faster than the same setup on WiFi. The ring is what makes distribution worth it.

8 Wiring It Into opencode

mlx_lm.server speaks OpenAI-compatible HTTP, and it auto-detects distributed mode (mx.distributed.init().size() > 1) — so serving the sharded model is literally the same command you run for one Mac. We launched it through mlx.launch and pointed opencode at it as a custom provider.

Fig 5. opencode → custom provider → rank 0 API → distributed generation.

opencode.json

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "mlx-dist": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "MLX Distributed (2x Mac mini, Qwen3-1.7B-4bit)",
      "options": { "baseURL": "http://127.0.0.1:8080/v1", "apiKey": "no-key" },
      "models": {
        "mlx-community/Qwen3-1.7B-4bit": { "name": "Qwen3 1.7B (distributed)", "tool_call": true }
      }
    }
  },
  "model": "mlx-dist/mlx-community/Qwen3-1.7B-4bit"
}

Verification before trusting it

  • opencode models → lists mlx-dist/mlx-community/Qwen3-1.7B-4bit.
  • One-shot /v1/chat/completions with tools → finish_reason: "tool_calls" with correct JSON args.
  • Streaming check → SSE chunks flow (opencode depends on streaming).
!
opencode does not hot-reload config. Config is read once at launch, and every tab in a session shares that frozen config. After writing opencode.json, quit opencode completely and reopen it from the project directory — otherwise your "new tab" searches in vain for mlx-dist while opencode models proves it exists.

9 Using It From Any Machine

Rank 0 was bound to 127.0.0.1 initially — invisible to the network. Rebinding to 0.0.0.0 and restarting made the API reachable at the Mac's WiFi address. Inference then verified over http://192.168.1.64:8080.

✓
Internal ↔ external split is real: the two Macs keep sharding over the Ethernet ring (10.0.0.x) while opencode on any laptop talks to rank 0 over WiFi (192.168.1.64:8080). Firewall disabled on the Macs, so nothing blocks the inbound connection.
!
Only rank 0 speaks HTTP. Because of server.py:1745, rank 1 (Mac B, 192.168.1.5) runs no listener at all — curl 192.168.1.5:8080 returns connection refused. You cannot use the second WiFi IP as the endpoint unless you flip the rank order in hosts.json.

Config for a remote laptop

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "mlx-dist": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "MLX Distributed (2x Mac mini, Qwen3-1.7B-4bit)",
      "options": { "baseURL": "http://192.168.1.64:8080/v1", "apiKey": "no-key" },
      "models": {
        "mlx-community/Qwen3-1.7B-4bit": { "name": "Qwen3 1.7B (distributed)", "tool_call": true }
      }
    }
  },
  "model": "mlx-dist/mlx-community/Qwen3-1.7B-4bit"
}

Drop it on the client as the project or global config (~/.config/opencode/opencode.json), restart, pick the model. Token usage per model is visible with opencode stats --models. One caveat: every token round-trips over WiFi from a wireless client, so expect the ~34s-class latency there — the 3.5s wired number only applies when the client sits on the wire too.

Mental model: rank 0 is the front door. SSH + API come in over WiFi; the moment a request lands, every token is computed in a coordinated dance over the Ethernet ring — and only rank 0 ever answers the door.

11 Observability — Grafana

There's already a k0s cluster on the same LAN (192.168.1.10 / cylon) running a full kube-prometheus-stack: Prometheus 3.4.1 (route prefix /prometheus) and Grafana behind a traefik ingress at thecylon.local. We explored two distinct "model stats" stories:

Fig 6. Two sources, one pipeline. The llama.cpp path ships metrics via ServiceMonitor; the MLX Macs now push/scrape into the local VictoriaMetrics stack.

Path A — llama.cpp model (already instrumented)

The llama namespace runs a llama.cpp coder.gguf server with --metrics and a ServiceMonitor scraping it every 15s. Rich llama metrics (llama_requests_total, llama_tokens_prompt_total, llama_tokens_predicted_total, tokens/sec, etc.) should already be flowing into Prometheus. Next step: verify the target is healthy, then import a community dashboard (e.g. llama.cpp Server Metrics #19237) into Grafana.

Path B — MLX Qwen3 on the Macs (working)

The two Mac minis sit outside the cluster, and mlx_lm.server has no /metrics endpoint — so we built the bridge ourselves. A local podman stack on rank 0 (observability/compose.yaml) runs VictoriaMetrics, an otel-collector, and Grafana:

ContainerPortRole
victoria-metrics:8428TSDB + scraping; Prometheus-compatible API & /vmui query UI
otel-collector:4317 / :4318OTLP receiver → prometheus_remote_write → VM
grafana:3000auto-provisioned datasource + MLX Cluster dashboard

Two paths feed the TSDB: the proxy and both hw agents expose /metrics that VM scrapes every 15s, and they also push OTLP (traces + metrics + logs) to the collector, which remote-writes them into VM. Everything is reachable from the LAN, so node B (rank 1) pushes its hardware metrics over WiFi to 192.168.1.64:4318.

cd observability
./setup.sh                      # generates vm-scrape.yml from your machine IPs
podman compose up -d            # victoria-metrics + otel-collector + grafana
open http://localhost:8428/vmui # query: mlx_requests_total
open http://localhost:3000      # Grafana (admin/admin) → "MLX Cluster" dashboard

The dashboard charts requests/min, TTFT p50/p95, tokens/min, token rate, hallucination-risk heuristics, tool calls, and per-node hardware (load, memory pressure, worker RSS, CPU temp) — with a single panel showing whether all three exporters (mlx-proxy, mlx-hw rank0, rank1) are up.

!
One OTLP gotcha: the exporter needs the full signal path — base endpoint http://192.168.1.64:4318 must be expanded to /v1/metrics (and /v1/traces, /v1/logs) or the collector returns 404 and silently drops everything. The proxy now does this itself via _sig_url().

12 Key Takeaways & Gotchas

wins
  • Direct Ethernet between Macs gives near-single-node speed (3.5s vs 1.4s) — distribution is affordable on Apple Silicon.
  • mlx_lm's OpenAI-compatible server makes opencode integration a pure config change.
  • Rank-0-only HTTP makes the external surface tiny and predictable.
  • Identical venvs + pinned versions = reproducible sharded loads.
  • Full observability pipeline (scrape + OTLP → VictoriaMetrics → Grafana) runs on podman — no cluster needed.
gotchas
  • mlx.launch --python is ignored in 0.32.0 — put the interpreter in the command.
  • No temperature kwarg on generate_step — use sampler.
  • opencode config is not hot-reloaded — full restart required; tabs share frozen config.
  • Default server bind is 127.0.0.1 — rebind to 0.0.0.0 for LAN access.
  • Node B (192.168.1.5) is compute-only; don't point clients at it.
  • No Thunderbolt cable meant no IP-over-TB — the gigabit cable was the practical ring.
