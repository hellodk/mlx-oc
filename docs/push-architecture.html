Push-Based Metrics from the Mac Minis

Moving mlx_* off central pull and onto an OTLP push path into the k0s cluster — design, risks, cutover.

What actually runs right now

Everything below was read off the live cluster and the repo, not assumed. The starting point matters because two properties of the current design are load-bearing for alerting, and push changes both.

Current — Central Pull
FactVerified state
OTLP metrics from the MacsNone. All five agents are prometheus_client pull endpoints — zero MeterProvider / OTLPMetricExporter in any of them. OTel there carries traces and logs only.
WhyDeliberate. The proxy docstring: “the proxy does NOT export OTLP metrics so that mlx_* series exist exactly once.”

Alerting41 rules in 6 groups. 5 of them key off up{job=…}, which only a scraper synthesizes.
The idea is sound, but it is three new pieces — not zero

“OTel scrapes all metrics and pushes to the gateway” describes a target state, not the current one. It needs: a collector on the Mac with a prometheus receiver, a metrics path out of the gateway into the cluster VictoriaMetrics, and a rewrite of the five up-based alerts. None of it is exotic — it is the standard agent/gateway pattern — but it is a data-plane migration with alerting consequences, not a config tweak.

Target architecture

One collector on rank0 does the scraping locally — the pull loop stays, it just moves from across the LAN to inside the box. Everything leaving the Mac is a push.

Target — Agent on the Mac, Gateway in the Cluster

Collector on rank0

The scrape config already exists — observability/vm-scrape.tmpl.yml ports over almost verbatim, which is the point: the same target list, the same labels, just executed locally.

# cluster/otelcol-mac.yaml
receivers:
  prometheus:
    config:
      scrape_configs:        # lifted from vm-scrape.tmpl.yml, unchanged
        - job_name: mlx-proxy
          static_configs:
            - targets: ["127.0.0.1:8080"]
              labels: {service: mlx-proxy, node: rank0}
        - job_name: mlx-hw
          static_configs:
            - targets: ["127.0.0.1:9102"]
              labels: {service: mlx-hw, node: rank0}
            - targets: ["10.0.0.2:9102"]   # rank1 over the direct link
              labels: {service: mlx-hw, node: rank1}
        # ... mlx-kv, mlx-supervisor, mlx-logtailer, sglang

exporters:
  otlphttp:
    endpoint: http://192.168.1.10:30318   # LAN, never the 100.x address
    retry_on_failure: {enabled: true}
    sending_queue:                        # survives a cluster restart
      enabled: true
      storage: file_storage

extensions:
  file_storage: {directory: /opt/mlx/otelcol-queue}

service:
  extensions: [file_storage]
  pipelines:
    metrics: {receivers: [prometheus], processors: [batch], exporters: [otlphttp]}
The disk-backed queue is the one thing pull gives you for free

A scraper that cannot reach a target simply records up 0 and moves on; nothing is lost on the target side because there is nothing buffered. A pusher that cannot reach the gateway drops data unless it has somewhere to put it. file_storage + sending_queue turns a cluster restart into a gap-free backfill instead of a hole in the graphs.

Gateway → VictoriaMetrics

The gateway's metrics pipeline currently ends at a prometheus exporter on :8889 that nothing scrapes. Add a second exporter rather than changing the first — other consumers may rely on it.

# charts/victoria-metrics-k8s-stack — otel-gateway config
exporters:
  prometheusremotewrite/vm:
    endpoint: http://vmsingle-monitoring.monitoring.svc:8428/api/v1/write
    resource_to_telemetry_conversion:
      enabled: true     # node / service / provider survive as labels

service:
  pipelines:
    metrics:
      exporters: [prometheus, prometheusremotewrite/vm]

Decisions

DecisionRecommendationWhy
Collector placementOne agent on rank0 scraping both nodes over 10.0.0.2rank1 runs only the HW agent and sglang. A second collector doubles the failure surface for two targets.
Gateway → storageprometheusremotewrite straight to vmsingleThe alternative — vmagent scrapes otel-gateway:8889 — re-introduces a scrape hop, and the exporter's cache means counters age at the scrape interval rather than the source interval.
Compose VictoriaMetricsDual-run, then decommissionKeeping both permanently violates the “mlx_* exists exactly once” rule the proxy was designed around.
vmalertVMRule CRs in hydra-mlxRules must live next to the data. Also satisfies the per-app-namespace rule.
Livenessabsent_over_time + collector self-telemetrySee tab 3 — this is the part that silently breaks.

What breaks, and the order to do it in

Two failure modes are worth more attention than the rest of the migration combined, because both fail quietly — the dashboards keep drawing and the alerts stay green.

Risk 1 — the five up alerts stop meaning what they meant

up is synthesized by whoever scrapes. Move the scrape onto the Mac and up{job="mlx-proxy"} still exists, but it now answers “can the collector reach the proxy?” — a question that has no answer at all when the Mac is off, because the thing that would have reported the failure went down with it. MLXProxyDown and MLXHardwareExporterDown would go permanently green on a powered-off Mac. That is strictly worse than today.

The push-native replacement is a data-absence check, which fires precisely when the whole path — Mac, collector, LAN, gateway — stops delivering:

# before — needs a central scraper
expr: up{job="mlx-proxy"} == 0

# after — fires when the series stops arriving, whatever the cause
expr: absent_over_time(mlx_up{service="mlx-proxy"}[3m])

# and keep one genuine pull target as a heartbeat: the collector's own
# self-telemetry, scraped by the cluster vmagent over the LAN. If this is
# the only thing you pull, you still get a real up{} for "is rank0 alive".
expr: up{job="mlx-otelcol"} == 0
Risk 2 — label translation is not lossless by default

The Prometheus receiver converts scrape targets into OTel resource attributes; the remote-write exporter converts them back. job and instance survive the round trip via the OTel↔Prometheus compatibility mapping (service.name / service.instance.id). Your custom target labels — service, node, provider — do not, unless resource_to_telemetry_conversion is on; without it they are demoted into a separate target_info series and every dashboard query and alert that groups by node silently returns nothing.

Do not take that on trust — including from me. Diff the label sets across both stores during the dual-run window:

# old path
curl -s 'http://192.168.1.64:8428/api/v1/series?match[]=mlx_up' | jq -S '.data' > /tmp/old.json
# new path
curl -s 'http://<vmsingle>:8428/api/v1/series?match[]=mlx_up'   | jq -S '.data' > /tmp/new.json
diff /tmp/old.json /tmp/new.json   # must be empty before you cut over

Cutover

  1. Land the folder fix firstA PR to thecylon-helm-charts setting sidecar.dashboards.folderAnnotation and provider.foldersFromFilesStructure. Unrelated to push, but it is the one thing already blocking the dashboards that are now in hydra-mlx.
  2. Run the collector on rank0 alongside the existing scrapeNothing is removed. The compose VictoriaMetrics keeps scraping; the collector pushes the same series into the cluster. Both stores now hold mlx_* — acceptable temporarily, not permanently.
  3. Add the remote-write exporter on the gatewaySecond exporter on the existing metrics pipeline; the :8889 prometheus exporter stays for whatever else uses it.
  4. Diff the label setsThe command above. An empty diff is the gate — if node or service is missing, fix resource_to_telemetry_conversion before going further.
  5. Rewrite the five up rulesabsent_over_time for the push path, plus one real pull target for the collector itself. Verify by powering down rank1 and confirming the alert actually fires.
  6. Move the 41 rules into hydra-mlx as VMRule CRsPortable rules.yml stays the source of truth per the multi-mode rule; the CR is a thin wrapper.
  7. Flip the datasourceOne line: url in infra/hydra-mlx/datasource.yaml moves from 192.168.1.64:8428 to the in-cluster vmsingle. Dashboards reference uid mlx-vm and need no edits — that is what the uid rewrite bought.
  8. Stop the compose scrape, then the compose stackOnly after the cluster path has held through a Mac reboot and a cluster restart. This is the step that restores “exactly once”.
Sequencing that matters

Step 7 before step 5 leaves you looking at cluster data with alerts still evaluating against a store you are about to turn off. Step 8 before step 4 makes the label diff unrecoverable — the old series are gone and there is nothing to compare against.

What this does not change

Traces and logs

Already push, already OTLP, already going to a gateway. Nothing in this design touches them.

The /metrics endpoints

All five stay exactly as they are. No code change on any agent — the collector scrapes what already exists.

The dashboards

Fifteen ConfigMaps in hydra-mlx, referencing uid mlx-vm. The cutover is a url change on one datasource.

The proxy's design rule

“mlx_* exists exactly once” holds again after step 8 — the collector scrapes the same endpoint the proxy always exposed, it does not add a second emission path.
