Distributed MLX Inference — 2 × Mac mini

Shard one small tool-calling model across two Macs with Apple MLX, then drive it through an agent loop with real tool calls. Plan v1.0

1 Goal

Run distributed inference of a small MLX model that understands tool calls across the two Mac minis. One model instance, its weights sharded across both machines (tensor parallelism). The agent demo asks the model a question that requires calling tools; the model emits a tool call, the script executes it, and the model produces the final answer — all with the compute shared over the LAN.

4 Implementation steps

1

Workspace on both nodes

Create /Users/dk/mlx-oc/dist on both (via ssh to .5).

2

Hostfile

hosts.json: rank 0 = localhost (127.0.0.1) on IP 192.168.1.64, rank 1 = 192.168.1.5. Ring listens on 192.168.1.64/5:32323.

3

Venvs + pinned deps

Python 3.14 venv on both; install mlx==0.32.0 mlx_lm==0.31.3 (pulls transformers 5.x, sentencepiece, protobuf, jinja2). ~2–3 min each.

4

Model on both nodes

Each node downloads mlx-community/Qwen3-1.7B-4bit into its HF cache (~1.1 GB each). Each rank needs the full weights to load & shard its local slice.

5

Scripts

agent.py — distributed agent loop; smoke.py — tiny all-gather ping test; copied to both nodes.

6

Smoke test

Run mlx.launch on the ping script — proves both ranks connect over the ring before loading any model.

7

Distributed agent run

Launch agent.py across both Macs; model sharded, tool loop runs on rank 0.

8

Baseline comparison

Run the same agent on a single node for a correctness + tokens/sec reference, and to quantify the TP-over-Ethernet trade-off.

5 The demo — tool-call agent

Two tools registered:

get_weather(city) → "24°C, partly cloudy" calculate(expression) → arithmetic result

Conversation:

[user] What is the weather in Tokyo, and what is 23 × 17? [rank0] model emits tool_calls → get_weather("Tokyo"), calculate("23*17") [rank0] agent executes both, appends results as tool messages [rank0] "The weather in Tokyo is 24°C, partly cloudy, and 23 × 17 = 391."

Tool calling is done the same way mlx_lm's OpenAI-compatible server does it: tokenizer.apply_chat_template(..., tools=tools) then parse <tool_call> blocks from the Qwen3 output.

6 Honest performance note

Tensor parallelism over 1 GbE Ethernet is latency-bound: every generated token requires an all-gather of hidden states between the Macs. For a tiny 1.7B model the network sync outweighs the compute gain, so the distributed run will likely be slower than a single node (expect single-node ≈ 40–80 tok/s; distributed may drop to a few tok/s).

That is expected and correct for this setup. The value here is demonstrating the sharding machinery works end-to-end with tool calls, plus an honest baseline to quantify the trade-off. If you later want speed, that's what Thunderbolt-5 RDMA + JACCL is for (the newer MLX 0.32 path) — not available on this 1GbE rig.

7 Risks & fallbacks

  • Version mismatch between nodes → versions pinned byte-for-byte; distributed init fails loudly, never silently.
  • Quantized weights + TP: Qwen3 shard() handles QuantizedLinear in mlx_lm (verified in source). If it still trips, fall back to the 8-bit/bf16 Qwen3-1.7B build.
  • Port 32323 blocked → pick another with --starting-port.
  • Model download time (~1.1 GB/node) → only on first run, cached after.
  • transformers 5.x install is heavy → isolated venv, no effect on system Python.
  • Old broken MLX installs are ignored entirely (fresh venv shadows them).
