The Fault Is Remote: Why rank1 Dies First

A five-token request crashed the box minutes after two agentic requests did — so the trigger was never just streaming+tools. macOS crash reports exist only on rank1 (an M4 16 GB paired with the M2 8 GB on the ring), the faulting thread is mlx’s own GPU stream thread, and the fatal pattern is a heterogeneous ring whose faster GPU faults, then poisons the device so the next request dies too — a readiness check of /v1/models cannot see it. Version skew is ruled out: both nodes run mlx 0.32.0 / mlx-lm 0.31.3. Decision 08-05: the ring stays — the plan moves to recovery hardening and load shaping.

Distributed MLX Tuning: The Lever Table, Applied and Measured

Before any tuning, the network premise died: the ring was already on dedicated Gigabit Ethernet (10.0.0.0/24 on en0, 0.48 ms RTT) — there was no WireGuard to remove. Then the lever table went from theory to implementation: decode/prefill concurrency, prefill step size, and prompt cache + a decode cap, each restarted and measured. Four levers, five restarts, zero errors and zero new metal_gpu_error crashes — with the structural options (pipeline, Thunderbolt, homogeneous pair) still deferred.

Opik Custom Dashboards: The mlx Project Gets a Live Health & Quality View

Can Opik itself turn the traces and judge scores into a dashboard we keep and version — no Grafana import needed? Yes. A 120-line idempotent script (tools/opik_dashboards.py) provisions a project-scoped dashboard for mlx — an Overview of latency p50/p90/p99, errors, tokens, cost and the feedback-score cards, plus six Trends time series including LLM spans broken down by model — with the two gotchas that only running it reveals: the self-hosted base URL needs an /api suffix (or nginx answers with the SPA’s index.html), and every widget id must appear in its section’s layout.
