The Other Half of the Story

Every request produces a trace in our proxy — and a stack of raw lines in logs/server.log that has never been shipped anywhere. The proxy’s Opik paths exist but are switched off, and its OTel logs pipeline ends at a podman logs stdout. This post is the plan to put the server’s side of the story next to the trace: enable tracing, add a filtered log tailer, and keep the flood gates closed.

1What is actually in Opik right now: nothing

We checked. The mlx project exists on the self-hosted Opik at 192.168.1.10:32173, and it holds zero traces and zero logs. Three separate gaps cause this:

  1. Tracing is wired but off. The proxy has two Opik paths — the SDK (--opik-endpoint) and OTLP ingestion (--opik-otlp-endpoint) — but start_server.sh only passes them when OPIK_ENDPOINT / OPIK_OTLP_ENDPOINT are exported. They aren’t. The running proxy has --otlp-endpoint (to our otel-collector) and nothing else.
  2. The proxy’s logs pipeline goes to a dead end. _setup_otel builds a LoggerProvider + LoggingHandler and an OTLPLogExporter — but only toward the local collector, whose logs pipeline terminates at a debug exporter. Meaning podman logs stdout. Not persisted. Not Opik.
  3. The server’s own log never leaves the machine. logs/server.log is read by exactly two processes: the KV-cache agent (turns lines into Prometheus gauges) and the supervisor (sniffs the tail for a crash reason). The raw stream is consumed for metrics and discarded.

So today, Opik can show you the proxy’s verdict on a request (TTFT, tokens, hallucination heuristics) but nothing about what the server saw — the Metal fault, the rank that walked off, the generation lines. The crash from post 9 is the canonical example: the whole story lived in server.log, and none of it made it to the trace system.

The gapMetrics measure, traces explain the request, and logs contain the incident — but only if they end up next to each other. Right now the third stream is silently thrown away.

2Why server logs belong beside traces

Consider the debugging questions our trace pipeline cannot answer today:

  • This trace is slow — did the KV cache miss? That answer is a line in server.log, not in any metric or span.
  • This request errored — was it a Metal fault, a rank down, or a model-side crash? The proxy only knows it got a 503. The typed reason is a [METAL] / [WARN] Node with rank… line.
  • What did the server actually generate vs. what the proxy reported? Generation lines carry the ground truth.

The honest caveat: raw server logs are noisy. In steady state our server.log is mostly HTTP access lines — one per request. Shipping every line into Opik would bury the signal in trivia and bloat the database. The plan therefore treats filtering as the core feature, not an afterthought (§4).

3The plan: one pipeline, two paths

One OTLP pipeline, two feeds — but not into the same sink. During implementation we confirmed what the docs hinted: Opik’s OTel ingestion is trace-only (/api/v1/private/otel/v1/logs → 404 while /v1/traces works; the opik SDK 2.2.13 has no log API). So the split is honest: traces → Opik, logs → the otel-collector’s durable JSONL file.

Path A — switch request tracing on

Set OPIK_OTLP_ENDPOINT=http://192.168.1.10:32173/api/v1/private/otel in start_server.sh. The proxy’s existing second span processor (mlx_metrics_proxy.py:137) then ships every chat completion to Opik stamped with OpenInference attributes.

Decision: use the OTLP path and keep the Opik SDK path off. Enabling both would create two traces per request (SDK + OTLP each log one). One pipeline is cheaper to reason about and shares its exporter stack with the log tailer. The SDK path stays documented as an optional fallback.

Path B — a server-log tailer (new)

New mlx_server_log_tailer.py, same shape as the KV-cache agent:

  • Opens logs/server.log, seeks to the current end on start (no backfill flood), then follows at a 500 ms poll. Optional --backfill N seeds the last N lines once.
  • Classifies each line by regex into severity + category.
  • Emits an OTLP LogRecord per qualifying line to the collector (:4318): body = raw line; attributes for severity, category, source (mlx_lm.server), service.name, mlx.node.name.
  • Exports self-health on :9106 (mlx_log_tailer_up, lines_total{severity,category}, shipped_total, dropped_total, errors_total) so a dead tailer is visible in VictoriaMetrics.

One more thing implementation surfaced: the supervisor was running mlx_lm.server with inherited stdout, so its output went into supervisor.log and server.log was never fed. The supervisor now redirects the server’s output into server.log — the file the KV agent, the tailer, and the crash-sniffer all read.

Why filter-firstIn steady state the filtered stream is a handful of lines per day — the 4B-era log is almost all HTTP access lines, which we drop by default. --include-http and --all are opt-in and documented as expensive (MBs/day under bench load).

5Keeping the flood out

  • Filter first — the default classifier already drops the dominant noise class.
  • Rate cap — token bucket, default --max-rate 50 lines/s. A crash-spam loop or --all cannot outrun the budget.
  • Backfill OFF by default — --backfill N exists only for initial seeding, so a tailer restart never replays the whole file into the pipeline.
  • Bounded queue — the SDK’s BatchLogRecordProcessor caps the in-memory buffer (2048 records); if the collector is unreachable we drop-and-count (dropped_total{reason="rate_limit"}), never unbounded buffering.
Scope notePhase 1 ships project-level logs — every record lands in the collector’s JSONL file, correlated to Opik traces by time and service attributes. Precise trace-attachment (a log line pinned inside its own trace) needs a request-ID that flows proxy → upstream → server.log → trace_id; mlx_lm.server doesn’t emit one today. That’s phase 2, explicitly deferred — as is a true Opik Logs tab, which needs an Opik version with a logs feature.

6Acceptance gates

  1. ./start_server.sh restart → status shows log_tailer RUNNING, :9106/metrics returns 200, mlx_log_tailer_up 1.
  2. One request → Opik shows exactly one new trace in mlx (no duplicates), with an LLM span carrying input/output/usage; the same request’s server lines appear in the collector’s JSONL file (podman cp otel-collector:/var/log/otelcol/mlx-server-logs.jsonl) with the right severity/category, and mlx_log_tailer_lines_total increments.
  3. VictoriaMetrics has an mlx-logtailer target up; the new MLXLogTailerDown and MLXLogTailerNotSending warning rules evaluate without firing.
  4. No regression: mlx_server_* and mlx_kv_* metrics unchanged; the SDK path stays OFF to guarantee one-trace-per-request.

7What we deliberately didn’t build

  • Trace-attached server logs — needs request-ID plumbing through the proxy and into server.log. Documented, not built.
  • Structured parsing of KV-cache/generation lines into typed attributes — phase 1 keeps the body as free text.
  • More alerting beyond MLXLogTailerDown / MLXLogTailerNotSending.
  • An SSH tail for rank1’s worker log — the distributed run’s output (including “Node with rank 1 exited”) is mirrored into rank0’s server.log; verified true during implementation, so no separate tail was needed.
