SLMs for the Team, and a Router in Front: Tickets, Dashboards, Builds — and a Three-Tier Escape Hatch to the Frontier

Two specialist small models (Jira/Confluence tickets & dashboards, mobile app builds) and a logic router in front that sends routine work to the local cluster and only pays for frontier reasoning when it’s actually needed. This is the shape of it: what “training an SLM” really costs, what a router is, and how the whole thing slots onto the infra this repo already runs.

SLMs fine-tuned 1–4B (not trained from scratch)Toolchain mlx-lm LoRA → MLX 4-bit → vllm-metalRouter LiteLLM or an extended vllm_session_proxyTiers SLM → local generic → frontier

1Yes, you can — but “train” means fine-tune

The two targets — a tickets & dashboards SLM for Jira/Confluence and a mobile build SLM for Gradle/Xcode/fastlane — are both excellent fine-tuning problems: they have narrow output formats, bounded vocabulary (JQL, JSON, build commands), and lots of repeated structure. That is the sweet spot for a small model.

ⓘ
From scratch vs fine-tune. Pretraining a 1–4B model from random weights needs billions of tokens and a GPU cluster you do not have. Fine-tuning (LoRA/QLoRA) a strong open base on a few thousand domain examples gives you a specialist that is 90% of the way there — and runs on one of these Mac minis in hours. Start from Qwen3.5-4B (already on the cluster), Qwen2.5-3B, or Llama-3.2-3B.

What fine-tuning does and doesn’t fix. It makes output format-reliable (well-formed tickets, valid JQL, correct JSON schema) and cheap. It does not add knowledge or reasoning. If the task is “turn these notes into a ticket following our template”, the SLM nails it. If it is “design the dashboard architecture for a new product”, that is frontier territory — and the router’s job is to know the difference.

2What a router is, and what OpenRouter is

A router is the layer between your clients and many LLM backends that decides which model answers which request. It is the load balancer + circuit breaker + cost controller of LLM traffic: classification, fallback chains, budgets, timeouts.

OpenRouter is a hosted router: one API key, one OpenAI-compatible endpoint, and it forwards to hundreds of models across many providers, with price/context filters and server-side routing. Zero self-hosting — you buy a black box. The alternative is a self-hosted router: LiteLLM proxy (config-file routing, fallbacks, budgets, OpenAI-compatible) or your own code.

For this cluster the answer is both, layered: a self-hosted router owns the local SLMs and the generic local model; it only talks to OpenRouter (or the frontier APIs directly) for the expensive tier.

3The three tiers and the routing logic

TierWhat runs itCostGood for
0 — specialist SLMtickets/dashboards model, mobile-build model (local cluster)~freeticket creation, JQL, dashboard JSON, build-error fixes, CI config
1 — local genericQwen3.5-4B on the ring~freerewrites, summaries, everyday chat, tool calling
2 — frontierGPT/Claude/Gemini via OpenRouter or direct APIpay-per-callhard reasoning, novel code, messy/long documents, escalation

The router’s decision is a small deterministic function — an SLM is not needed to make the call:

  1. Classify the task (regex + keyword, or a tiny local classifier: is_ticket / is_build_error / is_generic).
  2. Capability check: does it need long context, file access, or heavy tool use beyond the SLM’s schema? If yes → up-tier.
  3. Budget & latency: hard cost cap and timeout per request type.
  4. Fallback chain: frontier down or over budget → local generic; local failed twice → escalate to frontier.
  5. Stickiness: keep one session on one backend (the proxy already does this by session hash).
✓
Where it lives here. The fastest path is LiteLLM proxy as the front door with three model_list entries (the two SLMs + the generic 4B) and a router rule sending a task-matched model per request, with frontier as fallback. The zero-dependency path is extending vllm_session_proxy.py — it already balances sessions across backends; adding a task-classification tier is the natural next step, and the classifier can itself be the tiny local model. The last-mile classification (“is this a ticket? a build error? generic?”) is exactly what an SLM is good at, so the router can run on the cluster it routes.

4The bottom line

  • Feasibility: both SLMs are a realistic month-of-part-time project; data is the bottleneck, not compute.
  • Cost model: tier 0/1 traffic is nearly free on the Macs; only tier 2 spends money — and the router’s whole purpose is to make sure that spend is reserved for requests that actually need it.
  • Efficiency: two specialists sharing one cluster is the distributed serving this repo already does — same engine, same proxy, extra model files.
  • Deployment order: (1) stand up LiteLLM in front of the current 4B, (2) classify + fallback to a frontier API, (3) train SLM-A, serve it, route tickets to it, (4) train SLM-B, repeat.
