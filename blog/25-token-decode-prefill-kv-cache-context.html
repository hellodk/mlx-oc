Tokens, Prefill, Decode and the KV Cache: How They Bound Context Length

Every time we bump --max-model-len on this cluster we hit a wall that is pure arithmetic: the KV cache for 16,384 tokens is 0.56 GiB, and a node only has so much memory left after the weights and the engine overhead. This post puts token, prefill, decode, KV cache and context length on one page — with the real breakdown from the two-Mac ring that took us from 4,096 to 24,288.

Measured on rank0 (M2 8 GiB) · peer (M4 16 GiB)Model Qwen3.5-4B-MLX-4bit (hybrid, 8 full-attention + 24 linear layers)KV 32 KiB per tokenCeiling 24,288

1One request, three phases

A single LLM call is a small pipeline. The text prompt is first tokenized into integer ids — the model never sees characters, it sees token ids, and every length limit in a serving engine is counted in tokens, not words or characters (roughly 1 token ≈ 0.75 English words). Then the model runs twice, in very different modes:

PhaseWhat happensCost characterYou see it as
Prefillthe whole prompt is processed in one parallel pass; every layer reads all prompt tokens at once and writes their K/V into the cachecompute-bound; cost grows with prompt lengthTTFT (time to first token)
Decodeone token at a time, each step reading the entire accumulated context through attention before emitting the next idmemory-bandwidth-bound; roughly constant per tokentokens/sec, inter-token latency

On this ring the split is easy to see. A short prompt pre-fills in well under a second (TTFT p50 ≈ 0.3–0.6 s depending on node and concurrency), then decode streams at 26–32 tok/s single-stream. TTFT is almost entirely prefill; the steady drip after it is decode. Tools, streaming, and every turn of an agent are just many of these pipeline passes stacked together.

2The KV cache: what grows, and why

Attention works by comparing a query against keys and values of every previous position. During decode, step N would naively re-derive all N−1 previous K/V pairs — wasteful. So serving engines cache them: each layer stores, for every token seen so far, its Key and Value vectors. That cache is the KV cache, and it is the reason a "second token" is much cheaper than the first: prefill pays the full attention cost for the whole prompt, decode only pays for one new position against a cached context.

Two consequences shape everything else:

  • It grows by exactly one token per generated token. Bigger prompt or longer answer ⇒ bigger cache. The cache footprint is linear in total sequence length.
  • It is allocated in fixed-size blocks. This model's engine uses 528-token blocks at 17,301,504 bytes per block → ≈ 32 KiB per token (≈ 35.8 KiB with the hybrid state overhead counted). That number is a property of the model's layer count, head count and head dims — it does not shrink because the machine is small.

One subtlety specific to this model: Qwen3.5-4B is hybrid — only 8 of its 32 layers are full attention with a real KV cache; the other 24 use linear attention with a compact per-sequence state (here 51.5 MB/seq, lazily reserved). So the "KV cache" you see in the breakdown is only the 8-layer part, and the linear layers ride on a small fixed state instead of a growing cache.

⚠
Rule of thumb: memory_for_context ≈ tokens × bytes_per_token. Doubling the context doubles that line on the budget, no matter how fast the GPU is.

3Context length is one budget: input + output

Here is the confusion that bites most people: max_model_len is not a prompt limit. vLLM counts the total sequence — prompt tokens plus generated tokens must fit inside it, or the request is rejected. So a 24,288-token ceiling means, say, 23,264 tokens of input and 1,024 tokens of output — not "24 K of prompt".

This is why the opencode config on this cluster sets context: 24288, output: 1024: the client's context window and its output budget are two numbers drawn from the same single pool. An agent with a growing transcript + tool results + a reply consumes all three lines of that table at once.

4Where the ceiling comes from: the memory budget

The engine does this arithmetic at startup:

kv_budget = usable_metal − model_weights − engine_overhead − hybrid_state_reserve

then derives max_model_len from kv_budget / bytes_per_token. It is the least flexible number in the whole serving stack — weights and overhead are fixed for a given model and engine, so the only dials are total memory and the KV share of it. The price of the +33%: fraction 0.95 wires almost the whole 8 GiB machine to Metal. free memory hovers around 60–80 MB and the OS survives on compression. That is the true maximum for rank0 — 0.98 is not a "bit more", it is a likely crash.

5The experiment that made it concrete

At fraction 0.9, asking for 16,384 failed immediately:

ValueError: To serve at least one request with the model's max seq len (16384),
(0.56 GiB KV cache is needed, which is larger than the available KV cache memory
(0.53 GiB). Based on the available memory, the estimated maximum model length is 15312.

Every "more please" then became a hunt for memory, in order:

  • Lower max-num-seqs (4 → 2): the hybrid state reserve barely moved — available KV stayed 0.53 GiB. Dead end.
  • CPU KV offload: the module ships in this vLLM build, but no CLI flag and no Metal platform support. Dead end.
  • Quantized KV (--kv-cache-dtype): not exposed on the Metal backend. Dead end.
  • Raise the memory fraction (0.9 → 0.95): freed 0.29 GB → kv_budget 0.58 GB → 0.87 GB → ceiling 15,312 → 24,288 (a 24,576 probe reported the exact estimate).

One serving requirement made the number cluster-wide: the session proxy balances sessions across both backends, and vLLM hard-rejects any request above max_model_len. So both nodes run --max-model-len 24288, even though the 16 GiB peer could physically serve roughly 60 K+. The weakest node sets the contract.
