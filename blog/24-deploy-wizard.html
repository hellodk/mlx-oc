Post 24 · the input wizard

Deploy the MLX Cluster with a Wizard: tools/mlx-deploy.py + Ansible

Post 23 was the manual. This is the tool that does the manual for you: an interactive input wizard that asks for the node details, topology and versions, scans every node for prerequisites (and tells you the fix), then drives an Ansible playbook that builds the venvs, syncs the repo, stages the model and starts the ring — for one node or many.

Wizard tools/mlx-deploy.pyPlaybooks infra/ansible/cluster.yml + check.ymlModes interactive or --configNodes 1..N

1What you get

Deploying the cluster by hand (post 23) means: two venvs per node, pinned wheels, the model on every Mac, matching hostfiles, cluster.env, SSH keys, and a ring link that actually stays up. The wizard collapses all of that into answers to questions, and the playbook makes the answers true, idempotently, on every node at once.

It runs with plain python3 (the wizard writes its own YAML — zero third-party deps) and with ansible-core only (no extra collections).

Run the report alone with:

On this repo it correctly flags the gaps in the example config — e.g. rank1 has no python3.12 yet, and the example’s ring IP is not on rank0’s current interface — each with the one-line fix.

4What the playbook does

# from infra/ansible (the wizard runs these for you)
ansible-playbook -i inventories/generated/hosts.yml check.yml      # read-only report
ansible-playbook -i inventories/generated/hosts.yml cluster.yml    # prereqs + setup + start
ansible-playbook -i inventories/generated/hosts.yml cluster.yml --tags setup   # venvs only
ansible-playbook -i inventories/generated/hosts.yml cluster.yml --tags start   # ring only
ansible-playbook -i inventories/generated/hosts.yml cluster.yml --tags stop    # tear down

setup (every node): creates the two venvs, installs the pinned wheels, verifies mlx_lm imports, rsyncs the repo from rank0 to peers (same absolute path — see the callout), renders hosts.json / hosts_rev.json / cluster.env, and downloads or asserts the weights. start (rank0): runs ./cluster/start_server.sh and waits until :8081 and the proxy :8080 answer /v1/models.

!
The repo must live at the same absolute path on every node: mlx.launch and start_server.sh ssh the remote ranks with rank0’s paths, so a different path on a peer breaks the ring at launch (the same constraint post 23 called out for the hostfiles).

5Versions, decided from the blogs

  • Python 3.12 for the server venv on every node (posts 1, 23; INSTALL.md §8): macOS Local-Network privacy (TCC) silently blocks a third-party py3.14 binary from reaching local subnets when spawned over SSH (EHOSTUNREACH, no dialog) — and mlx.launch spawns the remote shard exactly that way. The proxy/telemetry venv defaults to 3.12 too so the whole cluster is one interpreter.
  • mlx 0.32.0 / mlx-lm 0.31.3 / mlx-metal 0.32.0 identical on every rank (posts 13, 14, 23). mlx-metal is a separate platform wheel — mlx alone is CPU-only.
  • Extras pinned to the repo’s versions: prometheus_client 0.26.0, otel 1.44.0/0.65b0, optional opik 2.2.13 + aiohttp + litellm (post 23).
  • Offline: install_method: wheelhouse + a wheelhouse dir installs with --no-index --find-links (INSTALL.md §2).

6Non-interactive: a config file

The wizard can run headless from the same JSON it can save (--save-config):

python3 tools/mlx-deploy.py --config infra/ansible/mlx-deploy.example.json --apply
python3 tools/mlx-deploy.py --config cfg.json --check     # report only
python3 tools/mlx-deploy.py --config cfg.json --no-run    # write config, don't touch

mlx-deploy.example.json is the complete schema: nodes (name, ssh, ring_ip, local), interconnect, server_bind_ip, model/model_dir/download_model, python_server/python_proxy, venv_server, repo_dir, sync_repo, install_method/wheelhouse, install_opik, resource floors, and the pins. Everything else falls back to sane defaults.

7Adding nodes to a live cluster

Yes — the ring reads its size from the hostfile at launch, so it is not fixed-size. To add a node: append it to mlx_cluster.nodes and the inventory (rank order = hostfile order, rank0 first), put the new Mac on the ring link with a static IP in ring_subnet, ssh-copy-id from rank0, then re-run cluster.yml — setup creates the venv, installs the pins, syncs the repo and stages the weights there, and start rebuilds the whole N-node ring.

Caveats (from the blogs): there is no hot-add — a node change is a restart of the stack (16); every node must hold the full weights (23); the ring syncs to its slowest member, so a heterogeneous pair is the documented crash source (13, 16); and distribution only pays off past a single node’s memory (19, 23).

8Single node works too

A one-entry nodes list runs the same playbook: mlx.launch with a single hostfile entry serves locally with no ring sync, and the whole stack — supervisor, proxy, hw/kv/logtailer telemetry — starts and verifies exactly the same way.
