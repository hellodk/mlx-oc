Setting Up the Two-Mac MLX Cluster, From Zero to a Working Ring

Everything needed to stand up the distributed MLX ring on two Mac minis and actually use it: the two venvs and why there are two Pythons, the network and hostfiles, model placement on both nodes, the one config knob that changes the model, every curl that proves it works, the load-test rigs, and the six gotchas that bite first-time builders.

Nodes 2 Mac minisVenvs 2 (py3.12 + py3.14)Ports 8080/8081/9102/9104/9105/9106Model one line in cluster.env

1What you are building

One logical model split across two Mac minis over the MLX ring backend, fronted by an OpenAI-compatible proxy that makes it observable. Six processes, three of them pure telemetry:

PieceRuns onPortNeeds
mlx_lm.server (via mlx.launch --backend ring)both nodes, sharded127.0.0.1:8081 (rank 0)~/venvs/mlx — Python 3.12
cluster/mlx_metrics_proxy.pyrank 00.0.0.0:8080repo .venv — Python 3.14
cluster/mlx_server_supervisor.pyrank 00.0.0.0:9105repo .venv
cluster/mlx_hw_telemetry.pyboth nodes0.0.0.0:9102repo .venv
cluster/mlx_kv_cache_agent.pyrank 00.0.0.0:9104repo .venv
cluster/mlx_server_log_tailer.pyrank 00.0.0.0:9106repo .venv

Two venvs, two Pythons, one reason: macOS Local-Network privacy (TCC) silently blocks the third-party py3.14 binary from reaching local subnets when it is spawned over SSH (EHOSTUNREACH, no dialog). The remote shard therefore runs on the py3.12 venv; rank-0-only processes use py3.14. Both venvs carry identical mlx 0.32.0 / mlx-lm 0.31.3.

2The network: two links, two jobs

Traffic is split so ring collectives never compete with management:

LinkSubnet (this repo)Carries
Ring — dedicated Ethernet (en0)10.0.0.0/24 — repo now uses 192.168.2.2 / 192.168.2.1model shards, per-token ring sync
Management LAN192.168.1.0/24SSH, telemetry scraping, proxy clients

Set static IPs (System Settings → Network → Ethernet → Manual, or sudo networksetup -setmanual "Ethernet" 10.0.0.1 255.255.255.0), then verify L2 reachability — ping 10.0.0.2 from rank 0 should be ~0.5 ms with 0% loss. A missing or flaky ring link is the #1 cause of "the ring keeps dropping" (post 21).

3Two venvs, both nodes

# server venv (Python 3.12) — BOTH nodes
python3.12 -m venv ~/venvs/mlx
~/venvs/mlx/bin/python -m pip install \
  mlx==0.32.0 mlx-lm==0.31.3 mlx-metal==0.32.0 prometheus_client \
  opentelemetry-api opentelemetry-sdk \
  opentelemetry-exporter-otlp-proto-http opentelemetry-proto \
  opentelemetry-semantic-conventions opentelemetry-instrumentation

# proxy venv (Python 3.14) — rank 0 only, at the repo root
cd mlx-oc && python3.14 -m venv .venv
.venv/bin/python -m pip install prometheus_client opentelemetry-*
# optional, for Opik tracing / agentic bench:
.venv/bin/python -m pip install opik==2.2.13 aiohttp litellm
!
mlx-metal is a separate platform wheel — installing mlx alone gives the CPU backend and no Metal/GPU acceleration. And use python -m pip, never the venv bin/pip script: its shebang can point at a path that no longer exists if the venv is ever moved.

4SSH and the hostfiles

ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519          # on rank 0
ssh-copy-id dk@192.168.1.5                                 # reach rank 1
ssh -o BatchMode=yes 192.168.1.5 true                      # must not prompt

Hostfile entry order is ring rank order. cluster/hosts.json (rank 0 side) and cluster/hosts_rev.json (the reverse file used on the remote) must be updated together whenever IPs change:

{
  "backend": "ring",
  "envs": [],
  "hosts": [
    {"ssh": "127.0.0.1", "ips": ["192.168.2.2"]},   # rank 0 = serving node
    {"ssh": "192.168.2.1", "ips": ["192.168.2.1"]}  # rank 1 = peer
  ]
}

Or regenerate automatically: ~/venvs/mlx/bin/mlx.distributed_config --hosts 127.0.0.1,<rank1> --over ethernet --backend ring --auto-setup. If mlx.launch ever fails, the same command without --auto-setup probes the ring link and prints whether a full ring is possible.

5The model lives on BOTH nodes

The ring shards weights across the two Macs, so rank 1 must hold a copy too. Either layout works; a plain directory is simplest:

huggingface-cli download mlx-community/Qwen3.5-4B-MLX-8bit --local-dir Qwen3.5-4B-MLX-8bit
sudo mkdir -p /opt/mlx-models && sudo cp -R Qwen3.5-4B-MLX-8bit /opt/mlx-models/   # both nodes

A missing weight file on rank 1 crashes the ring at load — verify with ls on each node before starting. For an air-gapped site, set HF_HUB_OFFLINE=1 and HF_HUB_DISABLE_TELEMETRY=1 at the top of start_server.sh.

6The one knob: cluster.env

Every script reads MLX_MODEL from cluster/cluster.env, so changing the model is one edit, one render, one restart:

MLX_MODEL=mlx-community/Qwen3.5-4B-MLX-4bit   # <-- change this line
MLX_SERVER_IP=192.168.1.5                     # rank 0 server bind
MLX_DEFAULT_TEMP=0.0                          # agentic/coding defaults to deterministic

./render-config.sh           # regenerate opencode.json from cluster.env
./cluster/start_server.sh    # start
./cluster/start_server.sh status

The same file carries the guardrails that stopped the post-22 Metal OOM: MLX_MAX_PROMPT_TOKENS=16000, MLX_MAX_TOKENS_CAP=4096, MLX_MAX_BODY_BYTES, optional MLX_API_KEY, and MLX_RATE_LIMIT. The proxy enforces all of them before the GPU ever sees a request.

7Start & verify

./cluster/start_server.sh                       # supervisor, ring, proxy, hw, kv, logtailer
curl -s http://127.0.0.1:8080/v1/models
curl -s http://127.0.0.1:8080/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"mlx-community/Qwen3.5-4B-MLX-4bit",
       "messages":[{"role":"user","content":"say hi"}],"max_tokens":16}'
curl -s http://127.0.0.1:9105/metrics | grep mlx_server_state    # expect 1.0
curl -s http://127.0.0.1:9102/metrics | grep mlx_hw_load1        # rank 0
curl -s http://192.168.1.5:9102/metrics | grep mlx_hw_load1      # rank 1
./cluster/stop_server.sh

The launch line in start_server.sh already carries the blog-16 tuning (--decode-concurrency 8 --prompt-concurrency 4 --prefill-step-size 512 --prompt-cache-size 2 --max-tokens 1024). The :8081 readiness check only proves rank 0 is up — the full ring picture lives in cluster/logs/server.log and the mlx_net_* ring counters.

8Use it: OpenAI-compatible, anything works

The proxy at http://<rank0-ip>:8080/v1 speaks the OpenAI protocol — streaming and non-streaming chat completions, with TTFT / token-rate / hallucination-risk recorded per request. Any OpenAI client can point at it:

# opencode, pointed at the cluster (rendered into opencode.json by render-config.sh)
opencode --model mlx-community/Qwen3.5-4B-MLX-4bit

# raw streaming chat
curl -sN http://127.0.0.1:8080/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"mlx-community/Qwen3.5-4B-MLX-4bit","stream":true,
       "messages":[{"role":"user","content":"Explain the ring topology."}]}'

One proxy detail matters for TTFT: it relays SSE with resp.read1() so it never waits for a full 64 KiB buffer before forwarding a chunk — without it, streaming TTFT looks like the whole generation time.

9Load test and smoke it

.venv/bin/python tools/bench.py --base http://127.0.0.1:8080/v1 \
  --model mlx-community/Qwen3.5-4B-MLX-4bit --iters 3 --label "ring"

.venv/bin/python tools/bench.py --concurrency 4 --max-tokens 256 --iters 5 --label "4-way burst"
.venv/bin/python tools/smoke.py        # ring connectivity test
.venv/bin/python tools/agent.py        # distributed tool-loop demo

What the numbers say on this hardware (from the README, measured against Qwen3-1.7B-4bit): the 2-node ring is ~3× slower than a single Mac for a small model — ring collectives dominate at 1.7B parameters. Distribution pays off only when the model is too big for one node’s memory. Aggregate throughput: single ~51.5 tok/s vs ring ~23.6 tok/s. For the 4B on the ring, blog 16 measured 18–29 engine tok/s depending on tuning.

10The Thunderbolt variant

The same cluster can run the ring over a TB4/USB4 cable instead of Ethernet. Post 21 documented the failure mode: link re-negotiations silently reverted the ring interface to link-local addressing and MTU 1500, leaking ring traffic out the LAN gateway (a 12–25 ms detour). The fix is an idempotent LaunchDaemon that re-applies 192.168.2.1/.2 and the 8000-byte jumbo MTU every 20 seconds on both nodes. It is worth it: TB4-vs-Ethernet showed +7.6% conc16 throughput.

11Observability (optional but the point of this blog)

cd observability
./setup.sh                # renders vm-scrape.yml from your IPs
podman compose up -d      # VictoriaMetrics + otel-collector + Grafana + vmalert + Alertmanager
open http://localhost:8428/vmui     # query UI
open http://localhost:3000          # Grafana (admin/admin) — "MLX Cluster" dashboard

The stack scrapes the proxy (:8080), both hw agents (:9102), the KV-cache agent (:9104), the supervisor (:9105) and the log tailer (:9106) every 15 s, evaluates 46 alert rules, and renders twelve provisioned dashboards. Proxy traces/logs also flow to Opik over OTLP when MLX_OTLP_ENDPOINT is set.

12The six gotchas that bite

GotchaWhat it does
TCC blocks py3.14 over SSHRemote shard must run on the py3.12 venv (~/venvs/mlx) — instant EHOSTUNREACH otherwise, with no dialog.
No mlx-metalmlx alone is CPU-only — GPU inference silently falls back to the CPU.
Hostfiles out of synchosts.json and hosts_rev.json must be edited together; entry order is ring rank order.
Model missing on rank 1Ring crashes at load with no useful message — verify weights on both nodes first.
Model bigger than the noderank 0 is memory-constrained (the post-22 crash was a 17,667-token prompt OOMing an 8 GiB node). Pick a quant that fits with KV, and keep the proxy guardrails on.
bin/pip stale shebangAlways use python -m pip; the venv bin/pip script breaks if the venv moves.
