Managing the MLX Cluster Lifecycle with Ansible: Check, Deploy, Start, Stop

One playbook, four tags, one inventory, zero hand-typed ssh… mostly. The full runbook for bringing the two-Mac-mini ring down and back up through infra/ansible — what each tag actually does, how to verify a clean stop, and the one process that looks alive after pkill but isn’t.

1What the stack is, before you stop it

The running stack is six components across two nodes. Knowing them by name is what makes a clean stop verifiable — every one of them is declared, with its host, port, health endpoint and pkill -f patterns, in the stack manifest cluster/mlx-stack.json (rendered by Ansible from the group_vars; nothing is hardcoded in a script anymore):

ProcessRuns onPortJob
mlx_server_supervisor.pyrank0:9105spawns the ring, restarts it with backoff, exports serving-status metrics
mlx.launch --backend ringrank0 (orchestrates)—shards mlx_lm.server across rank0 + rank1 over 192.168.2.0/24
mlx_server_launcher.pyrank0 + rank1—remote shard entrypoint (rank1 runs it over ssh)
mlx_lm.serverrank0:8081OpenAI-compatible model server for the loaded model
mlx_metrics_proxy.pyrank0:8080front-door proxy — the endpoint clients actually hit

mlx_server_log_tailer.pyrank0:9106flood-protected server log tailer

2The Ansible layout

Everything lives under infra/ansible/:

  • cluster.yml — the lifecycle playbook against the mlx_ring host group, with four tags: prereqs, setup, start, stop.
  • check.yml — read-only pre-flight report (no changes, no start).
  • inventories/generated/hosts.yml — rank0 (local connection) + rank1 (ssh as dk).
  • group_vars/all/mlx-cluster.yml — every node, model, port, pin and tuning value; the single source of truth.
  • roles/mlx-cluster/tasks/ — prereqs.yml, setup.yml, deploy.yml (start) + start_one.yml, stop.yml + stop_one.yml.
  • cluster/mlx-stack.json — the manifest: every component, its host, port, pidfile, logfile, health URL and kill patterns. Rendered by the setup tag; read by start and stop.

The role resolves each host’s entry from mlx_cluster.nodes[] and only rank0 (mlx_rank0_host) performs start/stop — it orchestrates the peers. Host names in the inventory must match mlx_cluster.nodes[].name.

ⓘ
Wizard-generated config. Both the inventory and group_vars are written by tools/mlx-deploy.py. Change nodes/model/ports through the wizard, or hand-edit both files together — not one.

3Stop the whole stack

From infra/ansible:

ansible-playbook -i inventories/generated/hosts.yml cluster.yml --tags stop

What runs: on every node, the stop tasks read the manifest and stop each component whose kill_hosts mentions that node — first the pidfile pid (for components hosted there), then every bracketed kill pattern (mlx[.]launch etc., so a pattern can never match pkill’s own command line). The server component lists all nodes in kill_hosts, because its supervisor spawns ring shards on the peers — that is how the remote mlx_lm.server / mlx_server_launcher processes get cleaned up too. cluster/stop_server.sh is now just a thin wrapper around ansible-playbook … --tags stop.

⚠
The process that outlives the playbook. The supervisor tears the ring down asynchronously — it terminates mlx.launch, waits up to 10 s, then ssh’s to each peer to kill the remote ranks (up to 15 s each) — so it stays alive for a few seconds after pkill. That is exactly why the playbook doesn’t just assert once: it waits (polling every 2 s, up to 30 s) for the process scan, the port scan and the pidfile scan to come back empty, and fails loudly if they don’t. A silent partial stop is impossible — and stop is idempotent, so already-down == pass.

Verify a clean stop — the playbook does all three of these on every node (this is the manual equivalent):

ps aux | grep -E 'mlx_lm|mlx_server|mlx_metrics_proxy|mlx_kv_cache|mlx_hw_telemetry|log_tailer|supervisor|mlx.launch' | grep -v grep
lsof -nP -iTCP -sTCP:LISTEN | grep -E ':8080|:8081|:910[0-9]'   # expect: no lines
ssh dk@192.168.2.2 'pgrep -fl mlx'                             # expect: no output

4Run it back up

First the read-only pre-flight — OS/arch/python/RAM/disk/model per node plus cross-node ping and passwordless-ssh from rank0, each with a suggested fix:

ansible-playbook -i inventories/generated/hosts.yml check.yml

Then the full bring-up (runs prereqs + setup + start). Setup is idempotent — venvs, pinned wheels, model weights and rendered hosts.json/cluster.env are only (re)created when missing:

ansible-playbook -i inventories/generated/hosts.yml cluster.yml

Or, if setup is already done, start alone:

ansible-playbook -i inventories/generated/hosts.yml cluster.yml --tags start

The start tag reads the manifest and each node starts its own components (idempotent — a port already listening skips the launch), waiting for each component’s health endpoint before moving on. rank0 launches the supervisor → mlx.launch ring → proxy → hw/kv/logtailer agents; rank1 launches its own hw telemetry. Then rank0 polls :8081/v1/models (up to 6 min) and :8080/v1/models (up to 1 min) until both answer 200, and prints the endpoint + model. cluster/start_server.sh start is now just a thin wrapper around ansible-playbook … --tags start.

✓
After a stop, --tags start is enough. The venvs, weights and rendered configs from the last setup are still on disk, so the ring comes back without the setup pass.

5The verification checklist

After --tags start, the same checks the playbook ran; after --tags stop they are enforced automatically by the playbook’s wait-and-assert pass.

  • Front door: curl -s http://127.0.0.1:8080/v1/models — returns the loaded model id (e.g. /Users/dk/mlx-models/Qwen3.5-4B-MLX-4bit).
  • Upstream: curl -s http://127.0.0.1:8081/v1/models — same list, proving the sharded server is up, not just the proxy.
  • Supervisor truth: curl -s http://127.0.0.1:9105/metrics — serving-status gauges.
  • Ring peers: ssh dk@192.168.2.2 'pgrep -fl mlx' — remote shard + telemetry present when up, empty when stopped.
  • Ports: lsof -nP -iTCP -sTCP:LISTEN shows 8080/8081/9102/9104/9105/9106 only.

6Gotchas from actually running it

  • Python interpreter discovery warnings at the top of every run — rank0 finds python3.14, rank1 /usr/bin/python3. Harmless here; the role pins every venv build to python_server/python_proxy in group_vars.
  • Stop outlives a single snapshot. The supervisor tears the ring down asynchronously (terminates mlx.launch, then ssh’s to every peer to kill remote ranks, up to ~25 s total), so a naive one-shot check would report a false clean. The playbook handles it by polling the process/port/pidfile scans until they come back empty (2 s × 15) before asserting — but a plain pkill + immediate start can still hit the old supervisor holding :9105 for a few seconds.
  • The launchd design doc (cluster/com.hydra.mlx-server.plist) is a not-yet-deployed daemon that would KeepAlive the supervisor. If you ever install it, --tags stop alone won’t hold — you’d launchctl bootout it too.
  • Repo sync skips secrets-ish dirs by design: rsync --exclude=.git/.venv/cluster/logs/__pycache__/inventories/generated; peer cluster.env is re-rendered by setup, not copied.
  • Host names are the join key. A mismatch between inventory host and mlx_cluster.nodes[].name silently skips tasks via inventory_hostname == mlx_rank0_host guards.
