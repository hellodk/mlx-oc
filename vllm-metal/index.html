Cluster Plan

vllm-metal on Two Mac Minis

A detailed, step-by-step plan to deploy an OpenAI-compatible vLLM cluster on the two Apple Silicon Mac Minis already running hydra, using the MLX backend and the existing VictoriaMetrics + Grafana observability stack.

Nodes hydra-svc-01 · hydra-svc-02 IPs 192.168.1.64 / 10.0.0.1 · 192.168.1.5 / 10.0.0.2 Backend vllm-metal (MLX) Status Draft plan

1Why vllm-metal on these two Mac Minis

Both Mac Minis already run the hydra MLX inference stack with mlx_hw_telemetry.py at :9102, mlx_metrics_proxy at :8080, and mlx_kv_cache_agent at :9104. Adding vllm-metal layers an OpenAI-compatible API on top of the same MLX runtime, so existing clients (LiteLLM, OpenAI SDK, curl) can reach the cluster through a familiar interface while the existing hydra telemetry continues to work unchanged.

4Node-by-node setup

Both nodes get identical vllm-metal configuration. The only differences are the IP address and the node name.

4.1 Prerequisites (both nodes)

  1. macOS 14+ (Sonoma) — required for MLX 0.19+ and vllm-metal compatibility.
  2. Python 3.11+ — already on both nodes via the hydra stack.
  3. vLLM 0.6+ with the mlx backend installed: pip install "vllm[mlx]"
  4. MLX 0.19+ — pip install mlx
  5. Model weights — download once to a shared location or replicate to each node: python -c "from huggingface_hub import snapshot_download; snapshot_download('meta-llama/Llama-3.1-8B-Instruct', local_dir='/models/Llama-3.1-8B-Instruct')"
  6. Firewall — allow inbound TCP on :8000 (vllm-metal API) from the LAN.

4.2 vllm-metal launch command

Run on each node as a launchd service (matching the hydra convention). Create /Library/LaunchDaemons/com.hydra.vllm-metal.plist:

{
  "Label": "com.hydra.vllm-metal",
  "ProgramArguments": [
    "/usr/local/bin/python3",
    "-m", "vllm.entrypoints.openai.api_server",
    "--host", "0.0.0.0",
    "--port", "8000",
    "--model", "/models/Llama-3.1-8B-Instruct",
    "--dtype", "float16",
    "--max-model-len", "32768",
    "--gpu-memory-utilization", "0.85",
    "--max-num-seqs", "8",
    "--enable-chunked-prefill",
    "--disable-log-requests"
  ],
  "RunAtLoad": true,
  "KeepAlive": true,
  "StandardOutPath": "/var/log/hydra/vllm-metal.out.log",
  "StandardErrorPath": "/var/log/hydra/vllm-metal.err.log"
}

Then sudo launchctl bootstrap system /Library/LaunchDaemons/com.hydra.vllm-metal.plist.

5Load balancing and routing

The load balancer sits at :8000 on the VPN (10.0.0.x) so all clients — including the existing LiteLLM gateway — reach it via a single endpoint. Two strategies are viable; the recommended one uses nginx for simplicity and health-check integration.

5.1 nginx configuration

upstream vllm_metal {
    server 10.0.0.1:8000 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8000 max_fails=3 fail_timeout=30s;
}

server {
    listen 8000;
    server_name vllm-metal.hydra.local;

    location / {
        proxy_pass http://vllm_metal;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    location /health {
        proxy_pass http://vllm_metal/health;
        proxy_next_upstream error timeout http_503;
    }
}

⚠ GPU memory contentionBoth vllm-metal and the existing hydra stack (mlx_metrics_proxy, mlx_kv_cache_agent) share the same unified memory pool. Set --gpu-memory-utilization 0.85 on vllm-metal and ensure the existing stack's memory footprint is accounted for. On a 16 GB Mac Mini, vllm-metal's 85% allocation leaves ~2.4 GB for the rest of the system — tight but workable. On 32 GB models, this is not a concern.

6.2 vm-scrape.tmpl.yml addition

Add a new scrape job for vllm-metal in the existing observability/vm-scrape.tmpl.yml:

- job_name: "vllm-metal"
  scrape_interval: 15s
  static_configs:
    - targets:
        - "192.168.1.64:8000"
        - "192.168.1.5:8000"
      labels:
        cluster: "hydra"
        service: "vllm-metal"
        environment: "production"

After updating the template, run ./cluster/setup.sh to push the new config to VictoriaMetrics.

7.2 Security considerations

  • No authentication on :8000 — vllm-metal's OpenAI server has no auth by default. Since the Mac Minis are on a private LAN/VPN, this is acceptable. For the VPN-facing endpoint, consider adding an nginx auth_basic layer or a lightweight API key check.
  • Firewall — macOS Application Firewall should allow incoming connections on :8000. Add via sudo /usr/libexec/ApplicationFirewall/socketfilterfw --addport 8000/tcp.
  • TLS — not required on the private LAN. If VPN termination happens at a gateway, TLS is already handled there.
  • Model weights — stored on local disk at /models/. No S3/GCS dependency. Replicate with rsync if updating models.

8Deployment timeline

Day 0 — Prerequisites Verify both nodes run macOS 14+, Python 3.11+, have network connectivity on :8000.
Day 1 — Model download Download Llama-3.1-8B-Instruct (or target model) to /models/ on both nodes. Verify with ls -lh /models/.
Day 2 — vllm-metal install pip install "vllm[mlx]" on both nodes. Smoke test: python -m vllm.entrypoints.openai.api_server --model /models/Llama-3.1-8B-Instruct --host 0.0.0.0 --port 8000 on one node.
Day 3 — launchd service Create com.hydra.vllm-metal.plist, bootstrap on both nodes, verify /health endpoint returns 200.
Day 4 — Load balancer Deploy nginx config on hydra-svc-01 (or a dedicated gateway). Test round-robin with curl -s http://10.0.0.1:8000/v1/chat/completions.
Day 5 — Observability Add vllm-metal scrape job to vm-scrape.tmpl.yml, run setup.sh, verify metrics in VictoriaMetrics, add Grafana panels.
Day 6 — Integration test Point LiteLLM at the new vllm-metal endpoint, run a full inference round-trip, verify metrics flow to Grafana.
Day 7 — Production cutover Update LiteLLM model routing to prefer vllm-metal for supported models, keep existing mlx stack as fallback.
